# Mobile & Windows support audit — 2026-10-02

**Question asked:** is the React Native/Expo app still a supported target? The mobile test
suite, the Maestro flows and the `app-releases` Android job disagree about whether it is alive.

**Answer: yes, both app targets are live and both are released — but neither was being verified
in CI, and one documented command was broken.** Android ships an APK and Windows ships an MSIX,
both from `app-releases.yml` on a `v*` tag, so neither can be treated as dead code. What was
missing was proof: until this audit, no push or pull request executed a single mobile or
Windows test.

## What each target actually is

| Target | Source in git | Native project | Release path |
| --- | --- | --- | --- |
| **Android** (`apps/mobile`) | tracked TypeScript/TSX (`App.tsx`, `src/`, `assets/`, `app.json`, `eas.json`) | **generated**, not committed — `.gitignore` lines 95–97 exclude `apps/mobile/android/`, `ios/` and `.expo/`, regenerated by `expo prebuild` | `app-releases.yml` → `android-apk` job (ubuntu-latest, Java 17) → signed APK attached to the GitHub release |
| **Windows** (`apps/windows`) | 37 tracked files including the WinUI solution `windows/HazardNet.sln`, plus generated MSBuild artefacts that *are* committed | **committed** — `apps/windows/windows/**` carries `.g.cpp/.g.h/.g.props/.g.targets` from MSBuild | `app-releases.yml` → `windows-build` job (windows-2022) → `.msix` + unpacked `.exe` |

`apps/mobile` is Expo SDK 51 (`expo ~51.0.28`, React Navigation 6, TanStack Query 5, FlashList).
Its version (`2.2.0`) is independent of the website's.

## Findings

### 1. The mobile test suite could not run from the documented command — **fixed**

`apps/mobile/jest.config.cjs` documents `npx jest --config apps/mobile/jest.config.cjs` from the
repository root, but its Babel option was `configFile: './babel.config.cjs'`, which Jest resolves
against the **current working directory**, not `rootDir`. From the root that loaded the root Babel
config, the React Native preset never applied, and every suite died in
`@react-native/js-polyfills/error-guard.js` with *Missing semicolon* — a Flow-syntax parse error
that reads like a broken dependency rather than a cwd bug.

Fixed by resolving the path against `__dirname`. **All 9 suites / 62 tests now pass in ~15 s**
(`npx jest --config apps/mobile/jest.config.cjs --ci`). The suite is healthy; only the invocation
was not.

### 2. Nothing ran those tests in CI — **fixed**

`ci.yml` had six jobs — `test-backend`, `test-frontend`, `test-pipeline-scripts`, `test-e2e`,
`verify`, `security-audit` — and none of them touched `apps/mobile` or `apps/windows`. The three
mobile suites that live at the repository root (`__tests__/mobile/*`) did run, because the root
Jest project collects them, which made CI look like it covered the app while the nine real
component suites never executed.

Added a `test-mobile` job. It runs with `--forceExit`: the suites pass but Jest hangs for a minute
after the last assertion because app hooks leave timers and async work open. That is real debt
(see §5) and is masked, not fixed, by the flag.

### 3. `prebuild:snapshot` pointed at a script that was never written — **fixed**

`apps/mobile/package.json` declared `"prebuild:snapshot": "node scripts/buildSnapshot.cjs"`.
There is no `apps/mobile/scripts/` directory, and nothing (no workflow, no other script) invoked
it, so the entry was a promise that had already been broken silently. Removed rather than
reimplemented: inventing a snapshot builder to satisfy a dead script would add behaviour nobody
asked for.

### 4. The release jobs patch `node_modules` by hand — **unchanged, documented**

Both release jobs copy dependencies into app-local `node_modules` because the workspace hoists
them to the root and Metro/MSBuild expect them locally:

- Android: `app-releases.yml` deletes any `metro.config.js`, **creates `metro.config.cjs` if it is
  missing**, and copies `expo` and `react-native` into `apps/mobile/node_modules`.
- Windows: the job copies `react-native-windows` and `react-native` into
  `apps/windows/node_modules`.

The Android job also patches Gradle for Expo SDK 51 compatibility inline. This works, but it means
the release path is not the developer path: a workspace install alone does not reproduce what CI
builds. The `metro.config.cjs` that job generates now exists in git (it did not when the workflow
was written), so the fallback is dormant — until someone deletes it.

### 5. Open handles after the test run — **open**

Jest reports *"did not exit one second after the test run has completed"*. The suites are
`act()`-clean enough to pass, but hooks such as `useSavedPlaces` (`setIsReady` after an async
resolve) leave pending work. Worth fixing before the suites grow: `--forceExit` hides a class of
bug that would otherwise show up as a hanging test.

### 6. Maestro flows exist and are wired correctly — **no action**

Four flows live in `apps/mobile/.maestro/` (`today-alerts-flow.yaml`, `offline-cache-flow.yaml`,
`tap-call-flow.yaml`, `perf-scenario.yaml`) and `test:maestro` points at the right relative path.
They are not run in CI (they need a device or emulator), which is a reasonable cost decision — but
it means the UI flows they cover are unproven between manual runs.

### 7. Windows has no test suite of its own — **open**

`apps/windows` has 37 tracked files and no tests. Root `__tests__/phase3WindowsApp.test.js`
asserts the *shape* of the Windows project (files, manifest entries, dependencies) rather than
behaviour, and the MSIX build only runs on a tag. A failed Windows build is therefore discovered
at release time, which is the most expensive moment to find it.

## Recommendation

Keep both targets. The signals that read as "abandoned" — no CI job, a broken documented command,
a dangling script — are all maintenance debt on a live product, not evidence of retirement. This
audit clears the three that block verification (§1–§3); §4–§7 are tracked in
`docs/ops/owner-actions.md` where an owner can pick them up.
