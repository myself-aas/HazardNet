# Deployment Verification — HAZARDNET_WEBAPP_DEPLOYMENT_GUIDE.md vs. Repository

- **Date:** 2026-09-12
- **Scope:** Phase-by-phase verification of every deployment artifact prescribed by `HAZARDNET_WEBAPP_DEPLOYMENT_GUIDE.md` (Phases 0–6 + Phase 7) against the actual repository, cross-referenced with `HazardNet.md` (master pipeline / edge-deployment converter) and the accepted ADRs.
- **Method:** file-existence checks + content greps only — no claims beyond what is verifiable in the tree.

## 1. Executive Summary

The deployment guide describes the **"New Architecture"** (Kaggle inference → GitHub Actions orchestration → Node data API → pre-computed forecasts, Docker Compose deploy, Prometheus + Grafana monitoring, daily runs, 64 districts + 490 upazilas, 10/20/30-day horizons). The repository implements **roughly half of it, along a different path**:

- **Production/compute side (Phases 0–1): mostly exists but is broken** — ~~both weekly workflows~~ ~~`weekly_hazardnet.yml` still references files/credentials that do not match the code~~ both issues resolved 2026-09-12: `weekly_forecast.yml` repaired (§3.1) and the broken legacy `weekly_hazardnet.yml` retired via ADR 0004 (§3.2).
- **Consumption side (Phase 3): never wired** — ~~no frontend code reads `/api/v1/forecasts` or the Firestore `forecasts` collection; the map/dashboard render static local data files plus on-demand `/api/predict` inference~~ **wired 2026-09-12**: `useLiveDistricts` (TanStack Query) overlays live `/api/v1/forecasts/bulk` data onto the static baseline in `LiveMapView` (with a 7/15-day horizon toggle + live-status chip) and `NationalOverview`; `/api/predict` on-demand inference remains. See backlog item 3.
- **Deployment topology (Phase 5): superseded** — ADR 0003 made **Vercel** the primary target; the guide's Docker Compose stack was never created.
- **Monitoring (Phase 4): partial** — prom-client metrics exist but lack the guide's key freshness gauge; no Grafana/Prometheus configs.

The single most important "remaining deployment" is therefore not a new component: it is **repairing the weekly pipeline and connecting the frontend to the forecast data**.

### 3.3 Latent ingest schema break — ✅ FIXED 2026-09-12 (found while wiring the frontend)

Discovered during backlog item 3: the Kaggle notebook's `results.append({...})` writes **dual-track columns** (`model_severity`, `physics_severity`, plus `division`, `pcode`) to `hazardnet_forecasts_latest.csv`, but the CSV ingest route validated `row.severity_score` — a column the notebook never emits. Consequence: even after the §3.1 repair, **every** row would have failed validation (422 "No valid rows found in CSV") and `/api/v1/forecasts/bulk` would have stayed empty permanently. Fix: shared parser `backend/utils/forecastRow.js` accepts both shapes (legacy `severity_score` **or** notebook `model_severity` as the severity source; optional `physics_severity`/`division`/`pcode` passthrough — preserving the README's dual-track severity story); `api/ingest.js` schema extended with the same optional fields. Regression-tested in `__tests__/forecastRow.test.js` + `__tests__/forecastsUpdate.test.js` (supertest multipart, mocked Firestore): notebook CSV → 200 with `records_updated` ✓.

## 4. Cross-reference: `HazardNet.md` (master pipeline) ↔ deployed artifacts

- **Edge Deployment Converter** (HazardNet.md, "HazardNet Edge Deployment Converter (Production Refactored)"): PyTorch → ONNX → TFLite INT8 + FP32 → `deployment_bundle/` with `labels.json`, `preprocessing_config.json` (normalization means/stds per band, input shape, dual outputs `hazard_logits`/`severity_pred`), normalization stats, and an inference script.
  - **Repo state:** `Models/` carries the FP32 bundle **minus INT8** — `hazardnet_fp32.tflite` (772 KB), `labels.json`, `normalization_stats.json`, `preprocessing_config.json` (band means match the converter's schema), plus generated `VERSION.json` (sha256 manifest, version `1.0.3+model.8d8d1b8758ce`). `hazardnet_int8.tflite` is absent — consistent with the README badge "TFLite FP32" and the server's 404-block on the int8 path. **Resolved 2026-09-12 (ADR 0007):** no INT8 variant will ever be deployed — TFLite's converter crashes on `CONV_3D` under INT8 (recorded in the master doc's converter, `MODEL_CARD.md`, and the SPA Documentation page), and the external bundle's `hazardnet_int8.tflite` is a *misnomer* (optimized-FP32 bytes). The FP32 bundle is the complete artifact set; the server guard keeps blocking the misnamed path (defensive).
- **Old Architecture (guide Part 2)** = HazardNet.md's edge design (GeoTIFF upload → preprocessing → TFLite). Remnants in repo: `/api/predict` tensor validation and the `UploadData.tsx` mock — but the frontend never constructs tensors; the "old" path is effectively dead UI + a live API used by the dashboard's on-demand inference.
- **Dual-track severity** (HazardNet.md Phase 2: model vs physics severity) survives in the ingest schema (`severity_score` + `confidence`) and the GET response's severity/confidence binning — but the guide's richer dual fields (`model_severity` / `physics_severity` per row) are **not** in the current Firestore write path (`backend/routes/forecasts.js` maps only `severity_score`).
- **Phase 1 ReliefWeb event extraction / Phase 3 dataset builder** (HazardNet.md) are offline research stages; nothing in the web app consumes them — training-side only.
