## 3 · P1 findings in detail

### 3.1 — Insufficient colour contrast · 45/45 routes · 2,388 nodes

The single most widespread defect. **There is no page on this site where a visit leaves no contrast violation.** It is not one bad token either: 21 distinct selectors fail.

| Selector | Routes |
|---|---|
| `.hover\:bg-amber-100 > span` | **20** |
| `a[href$="download"] > span` | 5 |
| `.p-4.bg-slate-50.rounded-2xl:nth-child(1) > .text-slate-400.uppercase.block` | 2 |
| `.text-center.text-\[10px\].text-slate-400` | 2 |
| `.px-3.rounded-full.py-1:nth-child(3)` | 2 |
| `.shadow-md` | 3 |
| (15 further selectors, 1 route each) | 1 each |

The top entry is a **shared component** — a span inside an `amber-100` hover surface — so one fix removes violations from 20 routes. The recurring pattern is `text-slate-400` (and `amber-*` text at small sizes) on light backgrounds: `slate-400` (#94a3b8) on white is **≈2.6:1**, well under the 4.5:1 required for body text and under 3:1 even for large text.

- **Page:** all
- **Element:** `.hover\:bg-amber-100 > span` (20 routes), plus 20 other selectors
- **Fix:** raise the text token. Replace `text-slate-400` with `text-slate-500` (#64748b ≈ 4.8:1 on white) for any text carrying meaning, and reserve `slate-400` for borders and icons. Re-run `scripts/qa/a11y-detail.mjs` — it prints the exact measured ratio and fg/bg pair per node.
- **File:** tokens live across `frontend/src/components/Navbar.tsx` and the shared footer; start from the selector list above.

### 3.2 — Invalid SVG geometry in the global header · 38/45 routes · **FIXED**

**Symptom.** 416 console errors, two per line, two lines per page:

```
Error: <line> attribute y1: Expected length, "undefined".
Error: <line> attribute y2: Expected length, "undefined".
```

**Root cause.** `MenuCloseIcon` in `frontend/src/components/ui/animated-state-icons.tsx` declares `<motion.line x1="10" x2="30">` with `y1`/`y2` present **only inside `animate`**. Before the first animation frame resolves, framer-motion's `renderSVG` writes the string `"undefined"` into the attribute. Captured at the moment of the write:

```
<line x1="10" x2="30" y1="undefined" y2="12" stroke="currentColor" stroke-width="2.5" …>
  at renderSVG (framer-motion.js:7755)
  at SVGVisualElement.renderInstance (framer-motion.js:7798)
```

**Why it was on every page.** The icon is rendered by `Navbar.tsx:173`, which is global — so this fired on 38 of 45 routes (the 7 exceptions are the auth/console shells that render no navbar).

**Fix.** Supply `initial` values so framer-motion always has a defined attribute to write, for both affected lines:

```diff
- <motion.line x1="10" x2="30" stroke={color} strokeWidth={2.5} strokeLinecap="round"
+ <motion.line x1="10" x2="30" stroke={color} strokeWidth={2.5} strokeLinecap="round"
+   initial={{ y1: 12, y2: 12, rotate: 0 }}
    animate={open ? { y1: 20, y2: 20, rotate: 45 } : { y1: 12, y2: 12, rotate: 0 }}
```

Adding the attributes statically is **not sufficient** — verified: the attributes appear in the DOM and framer-motion overwrites them with `"undefined"` anyway. `initial` is the load-bearing part.

**Verification.** Interception of `Element.prototype.setAttribute` across all 45 routes:

| | Before | After |
|---|---|---|
| Routes writing invalid SVG geometry | 38 / 45 | **0 / 45** |
| Invalid-attribute writes | 416 | **0** |

**Why the existing test suite never caught it.** `e2e/critical-paths.spec.ts › no JavaScript errors on critical pages` subscribes to `page.on('pageerror')` — *uncaught exceptions*. React reports invalid SVG attributes through `console.error`. The defect lived exactly in that blind spot. See the test report, §2.1.

### 3.3 — Controls with no accessible name · 5/45 routes · 340 nodes

axe names the element:

```
button-name:  div[title="Report Field Hazard Incident"] > .cursor-pointer
```

The floating action button (`frontend/src/components/ui/floating-action-button.tsx:102,110`) renders icon-only `<a>` / `<button>` elements with **no text and no `aria-label`**, at a measured **15 × 15 px**:

```jsx
<button className="flex items-center justify-center w-full h-full cursor-pointer">
  <Icon size={iconSize} className="text-muted-foreground …" />
</button>
```

- **Impact:** a screen-reader user reaches the primary "report a hazard" affordance and hears nothing. Critical, WCAG 4.1.2.
- **Fix:** `aria-label` on the button from the `label` the FAB already has in its data, plus a minimum 44 × 44 hit area (the wrapper can stay 15 px if a larger transparent hit area is added).

### 3.4 — Nested interactive controls · 5/45 routes · 970 nodes

Same component, second failure. The FAB nests a `<button>`/`<a>` inside a `div[title=…]` that is itself clickable, and axe flags every layer. 970 nodes is the largest node count in the whole review, and it is concentrated: fixing this one component clears the rule.

- **Fix:** one interactive element per action. Keep the `<button>` (with `aria-label`) and make the wrapper a plain `<div>` without a title-as-affordance.

### 3.5 — Map console routes have no `<h1>` · 4/45 routes · all viewports

`/live`, `/home`, `/home/overview`, `/forecast/overview` render **zero** `<h1>` at every viewport — the page title is a styled `<div>`, not a heading. These are the site's primary pages.

- **Fix:** mark the visible "Live hazard map" title (or the console's accessible name) as the page `<h1>`; visually it can stay identical.

Also in the same family: `/analytics` renders **two** `<h1>` elements, which is ambiguous for assistive tech and for search engines.

## 4 · P2 findings in detail

### 4.1 — Horizontal scroll: none. Layout overflow: present but bounded

The unusable-mobile-screen failure mode does **not** occur here:

| Measure | Result |
|---|---|
| Documents that scroll sideways (all 4 viewports, 180 loads) | **0** |
| Elements hanging past the right edge (non-map, refined) | 12 measurements, each a decorative blur or a clipped filter row |

**A measurement corrected mid-review, deliberately recorded.** The first pass reported **170** "horizontal overflow" and **1,433** "undersized touch targets". Inspecting the samples showed most were artifacts of how the probe was written:

- **Leaflet map markers** are absolutely positioned with transforms that legitimately sit outside the viewport; the map clips them and the document does not scroll. Excluded.
- **`Skip to main content`** is a `sr-only focus:not-sr-only` 1 × 1 skip link — correct behaviour. Excluded (≤ 1 px).
- **Inline prose links** ("All published alerts", 112 × 16) are text, not controls; WCAG 2.5.5 exempts them. Excluded.

`scripts/qa/layout-audit.mjs` redoes the measurement with those exclusions stated in code, and **this report quotes only the refined numbers**. The unrefined figures were not wrong about what is in the DOM — they were wrong about what constitutes a defect, and publishing them would have sent someone to fix a map marker.

One real item survives: on `/alerts` @375 px a filter row renders **465 px wide inside a 375 px viewport** (`div.flex.flex-wrap.items-center.gap-2`, "64 Districts / 8 Divisions / All / Flash F…"). It does not scroll the document because an ancestor clips it — which means **the last filters are cut off with no way to reach them**. Fix: let it wrap, or make it an explicit horizontally scrollable region with a visible affordance.

### 4.2 — Touch targets below 44 × 44 px · 44/45 routes @375 px · 504 controls

Measured at 375 px on 44 routes, controls only, prose links and skip links excluded:

| Rendered size | Count | Element |
|---|---|---|
| `button 15×15` | 38 | FAB icon buttons — **also unlabelled** (§3.3) |
| `a 154×40` | 36 | HazardNet wordmark link (40 px tall) |
| `a 190×36` | 27 | footer "Download Software & Apps" |
| `button 25×40` | 27 | narrow icon button |
| `a 140×38` | 25 | footer "GitHub Repository" |
| `a 41×16` | 25 | footer "Privacy" |
| `a 35×16` | 24 | footer "Terms" |
| `button 91×33` | 23 | "Feedback" |
| `a 111×29` | 20 | "Back to Live GIS" |
| `summary 301×20` | 18 | accordion summaries |

The pattern is **systematic footer and utility-link sizing**, not scattered error: the same ~10 controls recur across nearly every route. Raising the footer link line-height and padding fixes the majority at once.

*Coverage note:* this table is the 375 px pass (44 of 45 routes measured). The 768/1280/1920 passes were still running when this report was generated and are not quoted — touch targets are a pointer-accuracy question that only 375 px answers.

### 4.3 — Heading levels skip · 26/45 routes · 107 nodes

A consistent generator-level defect. Rendered heading order, desktop:

| Route | Order | Jump |
|---|---|---|
| `/districts/dhaka`, `/hazards`, `/privacy`, `/data-sources` | `1 → 2 → 2 → 2 → 4 → 4` | **h2 → h4** |
| `/retrospectives`, `/retrospectives/2024` | `1 → 4 → 4 → 4` | **h1 → h4** |
| `/this-route-does-not-exist` | `1 → 4 → 4 → 4` | **h1 → h4** |
| `/analytics/food-security` | `1 → 4 → 4 → 4` | **h1 → h4** |
| `/archive`, `/history`, `/events` | `1 → 3 → 3 → 3` | **h1 → h3** |
| `/faq` | `1 → 2 → 4 → 4` | h2 → h4 |

Nearly every **generated** page (`/districts/:id`, `/hazards/:slug`, `/retrospectives/:year`) goes `h1 → h2 → h4`; the sub-headings are `<h4>` with no `<h3>` level above them. Because these pages come from one generator (`scripts/build_content_engine.mjs`), the fix is one template, not 60 pages. `/archive` — the new page in this branch — skips `h2` and is a genuine bug of mine.

### 4.4 — Unlabelled `<select>` · 2/45 routes · critical

16 `<select>` elements with no accessible name (`select-name`, WCAG 4.1.2). A screen reader announces "combobox" and nothing else. Fix: associate a `<label>` or add `aria-label`.

### 4.5 — Text at 10.5–11 px

Smallest rendered text per route:

| Size | Route(s) |
|---|---|
| **10.5 px** | `/signup` (all viewports) |
| 11 px | `/forecast/district/dhaka`, `/alerts`, `/analytics`, `/status` |

Distribution across 180 measurements: 11 px × 28, 12 px × 135, 13 × 12, 14 × 1, 10.5 × 4. 12 px is already at the low end for data-dense UI; **10.5 px is below any readable minimum**, and it coincides with the low-contrast `text-slate-400` pattern from §3.1 — small *and* faint.

### 4.6 — Scrollable regions with no keyboard access · 10/45 routes

`scrollable-region-focusable` (WCAG 2.1.1) on 22 nodes, typically `.overflow-x-auto` wrappers around wide tables. A keyboard-only user cannot scroll them. Fix: `tabindex="0"` plus `role="region"` and an accessible name.

### 4.7 — API failures that reach the browser as bare 4xx/5xx

| Endpoint | Status | Routes | Cause |
|---|---|---|---|
| `POST /api/predict` | **422** | `/live`, `/home`, `/home/overview`, `/forecast/overview`, `/forecast/my-districts` | contract mismatch — see the test report §3.1 |
| `GET /api/v1/weather?lat=…` | **500** | `/forecast/district/dhaka` | upstream `fetch failed` in `backend/utils/openMeteo.js:199`, uncaught by `backend/routes/weather.js:26` |
| `GET /api/v1/alerts?fresh=…` | **504** | `/forecast/district/dhaka` | backend does not answer inside the dev-proxy timeout |

This is a design finding as much as a backend one: **the page renders normally while its data requests fail.** The district brief shows a full-looking layout with no indication that the weather and alert panels are empty because the API refused. It should show the degraded state it already knows how to describe — the same honesty the `/status` page applies to artifacts.

### 5.2 Environmental failures the UI does not acknowledge

- **Basemap CDN unreachable** → the service worker answers `504 (Tile Unavailable Offline)` **3,611 times across 5 map routes**. The map degrades to a blank grid with no explanation. The offline tile fallback is real engineering; it is just invisible. **Recommendation:** when tiles fail, show a one-line banner ("basemap unavailable — district data still live"). This is a P2 product finding: a user on a poor connection sees a broken-looking map instead of a stated limitation.
- **Firebase/GA unreachable** → 639 `ERR_FAILED` + 526 `ERR_CONNECTION_CLOSED` + `TypeError: Failed to fetch` on all 45 routes. Third-party, so not a defect — but a corporate-network or restricted-region user gets the same console noise with no explanation.

## 6 · What was fixed during this review

### 6.1 Invalid SVG geometry in the global header — fixed, verified

`frontend/src/components/ui/animated-state-icons.tsx` — `initial` values on the two `motion.line` elements in `MenuCloseIcon`. 416 errors on 38 routes → **0**. Full detail in §3.2.

Middle-detail worth recording: the first attempted fix (adding `y1`/`y2` as static attributes) **did not work** and was caught by re-running the interception probe rather than by assuming success. Framer-motion overwrites the attribute regardless; only `initial` works.

### 6.2 `/archive` was invisible to search — fixed, verified

The new archive page was **absent from every SEO surface**:

| Surface | Before | After |
|---|---|---|
| Generated sitemap | 89 URLs, no `/archive` | registered in `site-routes.json` |
| Static `public/sitemap.xml` | 15 URLs, no `/archive` | `/archive` added |
| `<title>` | `HazardNet` (shell default) | *Historical hazard archive for Bangladesh, 2000–2025* |
| `meta description` | generic shell copy | archive-specific, 2,931 / 64 / 8 / 251 |
| `link[rel=canonical]` | **absent** | `https://www.hazardnet.live/archive` |
| JSON-LD | none | `WebSite, Organization, Person ×3, WebPage, BreadcrumbList` |
| `og:title` | shell default | page-specific |

Root cause: `frontend/src/content/site-routes.json` is the single source of truth consumed by both `frontend/scripts/prerender.mjs` (static HTML + sitemap) and `usePageSeo` (client-side navigation). The new page was never registered in it, and never called `usePageSeo`. Fixed in both places, plus the dev-server sitemap fallback. Aliases `/history` and `/events` deliberately resolve to the **same** canonical so three URLs do not compete.

Verified in-browser on all three aliases: correct title, canonical, description, robots and JSON-LD graph; no boundary; no console errors.

### 6.3 Three compile errors — fixed

`npx tsc -p frontend/tsconfig.json --noEmit` was **failing on this branch** before this review (exit 2):

```
frontend/src/lib/forecasts.ts(394,3): error TS1117: An object literal cannot have multiple properties with the same name.
frontend/src/pages/HazardArchivePage.tsx(122,22): error TS2322: Property 'items' does not exist on type 'BreadcrumbsProps'.
frontend/src/pages/HazardArchivePage.tsx(170,20): error TS2322: same
```

- The duplicate `khagrachari` key was a genuine duplicate I introduced in the previous session's district-alias fix.
- `Breadcrumbs` takes `customItems: { label, path }[]`, not `items: { label, to }[]` — my page passed the wrong prop shape twice.

All three fixed; **`tsc --noEmit` now exits 0**. `eslint` on the touched files is clean.

**Correction (phase 2, verified): an earlier draft of this section said no CI gate would have caught
these.** That was wrong, and the correction matters more than the original claim. `ci.yml` already has
a `verify` job — *Code Quality & Build* (`ci.yml:388`) — that runs `npm run lint`
(`tsc -p frontend/tsconfig.json --noEmit`, `package.json`), `lint:eslint`, `check:rag-freshness`,
`check:embargo`, `archive:check`, `archive:rag:check`, then `npm run build` + `check:bundle`
(`ci.yml:421–504`). It would have failed on all three errors.

The real finding is narrower and more useful: **the branch had never been pushed, so that job never ran
on it, and neither of the local review passes invoked the same commands CI does.** The process fix is
therefore not "add a type gate" — it is "run the CI `verify` suite locally before declaring a pass
complete, and keep the branch pushed so the gate actually executes" (§8). The genuinely missing gates
are named in §8: axe, `console.error` coverage in E2E, the layout invariant, and a production-mode
smoke test.

One observed error boundary (`tablet /history`, `usePageSeo is not defined`) was a **transient of my own live editing** during the sweep — the `usePageSeo` call landed microseconds before its import. Re-verified afterwards: `/archive`, `/history`, `/events` all render clean at 768 px with zero page errors. Recorded here because a defect that appears in the raw data and is then explained away should be explained on the record, not deleted.

### 9.4 The blind spot that made phase 2 necessary

The pre-existing gate — `e2e/critical-paths.spec.ts › no JavaScript errors on critical pages` — listens
to `page.on('pageerror')` only. That event fires for **uncaught exceptions**; React reports invalid
SVG attributes through **`console.error`**. The `MenuCloseIcon` defect (§3.2, fixed here) fired twice
per render on 38 of 45 routes and passed that gate untouched. Phase 2 asserts on console output,
failed responses, and `pageerror`, which is why its final run reports **11 failures against an application whose pre-existing 4-route gate was green** (15 before the harness corrections recorded in test report §4).
