### 2) Formatting and Linting

- Formatter: **Prettier 3** — `.prettierrc`: `printWidth: 120`, `singleQuote: true`, `trailingComma: "all"`, `semi: true`, `tabWidth: 2`, `arrowParens: "always"`, `endOfLine: "lf"`. Run via `npm run format` (scoped to `frontend/src/**/*.{ts,tsx}`, `backend/**/*.js`, `api/**/*.js`).
- Linter: **ESLint 9 flat config** (`eslint.config.js`): `@eslint/js` recommended + `typescript-eslint` recommended + `eslint-plugin-react-hooks` (recommended) for TSX; formatting deliberately left to Prettier ("no stylistic rules here").
- Most relevant enforced rules: `@typescript-eslint/no-explicit-any: warn`, `@typescript-eslint/no-unused-vars: warn` (ignore `^_` prefixed), `no-console: warn` (allow `warn/error/info`; **off** for `backend/`, `api/`, `utils/`, `scripts/`, configs, `e2e/`); browser globals for frontend sources, serviceworker globals for SW files, jest globals for tests, node globals for backend — global groups fixed during the re-audit (finding N-1).
- Run commands: `npm run lint` (tsc `--noEmit` type-check), `npm run lint:eslint` (ESLint, 0-error policy blocking in CI), `npm run format`.
- TypeScript strictness: `frontend/tsconfig.json` — `"strict": true`, `target/module: ESNext`, `moduleResolution: "bundler"`, `jsx: "react-jsx"`, `skipLibCheck`, `forceConsistentCasingInFileNames`, `types: ["vite/client", "node"]`, path alias `@/* → src/*`.
- Ignores: ESLint skips `dist`, `node_modules`, `**/*.cjs`, `references/`, `skills/`, `rag_pipeline/`, `kaggle_notebooks/`, `app/`, `docs/`, `Models/`.

### 3) Import and Module Conventions

- Import grouping/order: no enforced plugin (no `import/order` rule); in practice React/library imports first, then local modules — e.g. `frontend/src/App.tsx`, `frontend/src/components/LiveMapView.tsx`.
- Alias vs relative policy: frontend may use `@/` alias (mirrored in `tsconfig paths` and Vite `resolve.alias` for shadcn components — `frontend/vite.config.ts`); observed code mostly uses **relative** imports (`../context/AuthContext`, `../data/bangladeshDistricts`). Backend uses relative ESM imports exclusively (`./routes/forecasts.js` with explicit `.js` extensions).
- Public exports/barrel policy: no barrel `index.ts` for frontend; pages/components use default exports (`export default function Navbar`), shared logic uses named exports; backend uses named exports for middlewares/utils and default export for the Express `app` (`backend/server.js`).
- `import type { … }` used for type-only imports (e.g. `AuthContext.tsx`, `DistrictDetailPage.tsx`).
- Cross-package imports: `api/*.js` (serverless) import from `../backend/*.js` — the `api/` layer must stay thin.

### 4) Error and Logging Conventions

- Error strategy by layer:
  - **Boot**: loud, early, non-fatal env assertions — `backend/server.js` `assertEnvironment()` logs `[config] …` warnings/problems (SEC-06).
  - **Routes**: try/catch returning structured JSON `{ error: string }` with proper status (400/405/422/429/503); auth gates fail **closed** (`verifyApiKey` returns 503 when key unset — `backend/utils/apiKeyAuth.js`).
  - **AI services**: never throw upward — cascade to the next provider tier, finally to a deterministic heuristic (`backend/utils/ai_fallback_engine.js`); advisory agent falls back to canned text (`backend/services/advisoryAgent.js`).
  - **Frontend**: `ErrorBoundary` component + `react-hot-toast` for user-visible failures (`App.tsx`, `LiveMapView.tsx`); `console.error` in service worker registration (`main.tsx`).
- Logging style: tagged `console.*` prefixes identifying the module — `[config]`, `[inference]`, `[tfjs]`, `[AdvisoryAgent]`, `[AI Fallback Engine]`; shared `utils/logger.js` wraps `[INFO]/[ERROR]`. Prometheus metrics for model load time and request counters (`backend/metrics.js`, `/metrics`). No structured logging library (comment in `utils/logger.js`: "can be swapped for winston or pino").
- Sensitive-data redaction: invalid JWTs are swallowed without leaking failure reasons ("never leak why upstream" — `backend/middleware/supabaseAuth.js`); no other explicit redaction framework `[TODO]`.

### 5) Testing Conventions

- Test file naming/location: co-located `__tests__/<Name>.test.ts(x)` in frontend; root `__tests__/<area>.test.js` for backend/serverless; e2e in `e2e/*.spec.ts` (excluded from Jest via `testPathIgnorePatterns`).
- Mocking strategy norm: `node-mocks-http`/`supertest` for backend route tests; Testing Library for React; a **Proxy-based mock Supabase client** keeps the app renderable when env is unconfigured (`frontend/src/lib/supabase.ts`); no MSW/network-layer mocking.
- Coverage expectation: Jest global coverage gate — statements 32, branches 35, functions 30, lines 31 (`jest.config.cjs`, "ratchet upward as tests land").

### Repo-specific documentation conventions

- Decisions are recorded as ADRs in `docs/adr/` (0001–0007, status lines "Accepted"/"Proposed"; later ADRs also carry execution + verification checklists — e.g. 0002 expand-phase, 0005/0006 phase-8 implementation).
- Audit/remediation programs are documented with finding IDs (SEC-xx, P0/P1/P2/P3, ARC, ML, FE, QA, OPS, BE, N-x) that are referenced **inside code comments** (e.g. "SEC-06", "P3-6", "FE-01", "ML-01", "QA-02") — when touching code, keep the finding-ID comments; they trace behavior to the audit trail in `docs/audits/`.
- Cross-file "single source of truth" rules are enforced by convention + comment: one Firebase config literal (`frontend/src/lib/config.ts`), one SQL migrations home (`scripts/db/`).
