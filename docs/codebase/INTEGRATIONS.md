### 3) Secrets and Credentials Handling

- **Credential sources:** environment variables only. Locally `.env` (never committed;
  `.env.example` is the template and the only env file tracked). In CI: repository **secrets**;
  in production: the **Vercel project environment**. `docs/ENVIRONMENT_SECRETS.md` is the policy.
- **Committed non-secret identifiers:** `firebase-applet-config.json` (Firebase web config — public
  by design; the same values are the fallback defaults in `frontend/src/lib/config.ts`) and
  `firebase-blueprint.json`. The Firebase web API key is intentionally public; the service account
  is not in the tree.
- **Hardcoding checks:** `scripts/check-secrets.sh` (leak scanner) runs in the `security-audit` CI
  job; `scripts/security_audit.sh` is a broader local audit; `scripts/verify-actions-secrets.sh`
  (plus `.github/workflows/verify-secrets.yml`) verifies the *shape and presence* of every secret
  the workflows reference without printing values; `apps/mobile/src/lib/security/sanitize.ts`
  asserts no secrets in the bundle in dev builds.
- **Redaction in code:** `redactSmsUrl()` replaces gateway keys with `<redacted>`;
  `redactTelegramUrl()` masks `/bot<token>/`; `maskNumber()` masks subscriber numbers
  (`backend/alerts/channels/sms.js`, `telegram.js`).
- **Rotation/lifecycle:** `[ASK USER]` — no documented rotation cadence. The only expiring
  artefacts are the npm advisories in `audit-exceptions.json` (each entry carries an `expires`
  date; the gate fails on expired entries).

### Auth flow (browser → API)

1. `AuthProvider` (`frontend/src/context/AuthContext.tsx`) holds the Firebase user; pages/components
   call `getIdToken()` where an authenticated call is needed.
2. `attachFirebaseAuthUser` (`backend/middleware/firebaseAuth.js`) verifies the bearer token and
   attaches `req.user` **without requiring it** — published alerts and forecasts are public; the
   review queue and AI routes are identity-aware (`dynamicAiLimiter` tightens the bucket for
   signed-in callers).
3. Privileged writes use a separate, non-Firebase mechanism: `verifyApiKey()` against
   `BACKEND_API_KEY` with a timing-safe comparison, fail-closed (503 when unset).
4. Firestore access from the browser is governed by `firestore.rules` (default-deny at the root;
   per-collection owner/superadmin predicates with field-budget validators).
