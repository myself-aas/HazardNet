### 3) Secrets and Credentials Handling

- **Credential sources:** environment variables only, in three places —
  Vercel project env, GitHub Actions secrets/variables, and a local `.env` (gitignored).
  `docs/ENVIRONMENT_SECRETS.md` is the setup guide; `.env.example` is the shape contract
  (**38 variables, all committed empty**). `npm run check:env` (`scripts/validate_env.mjs`)
  asserts that `.env.example` documents every required `VITE_FIREBASE_*` variable and that
  `frontend/src/lib/config.ts` maps them — **measured passing at HEAD**.
- **Hardcoding checks:**
  - The only committed credential-shaped literals are **Firebase web config values**
    (`frontend/src/lib/config.ts:20-29`, `firebase-applet-config.json`, `firebase-blueprint.json`).
    These are public by design — `config.ts` says so, and calls the removed second project
    (`src/firebase.ts`) "the cautionary tale".
  - `backend/utils/vapid.js:9` has a `DEFAULT_PUBLIC_KEY` fallback and a
    `mailto:admin@hazardnet.org` contact default — a **public** key and a contact string, not a secret.
  - The project id `hazardnet-aas48424` and the RTDB URL appear in source as fallbacks
    (`backend/db.js:50`, `frontend/src/lib/config.ts`).
  - Gates: `scripts/check-secrets.sh`, `scripts/security_audit.sh`,
    `scripts/verify-actions-secrets.sh` (static secret-reference audit), the
    `scripts/tests/test_secret_scan.py` suite, `.github/workflows/verify-secrets.yml`
    (dispatch-only) and `secret-rotation-audit.yml` (monthly).
- **Rotation / lifecycle:** **known and instrumented, but never exercised.**
  `docs/ops/secret-rotation.md` sets a cadence per credential; `data/security/secret-rotation.json`
  is the register (`version 1`, `updated_at 2026-10-02`, `grace_days 14`, `warn_days 30`);
  `npm run check:rotation` reports it. **Measured at HEAD: `15 credentials · 0 overdue ·
  13 unrecorded`** — every `last_rotated` is `null`, which the register's own note defines
  precisely: *"`last_rotated: null` means the rotation has never been recorded — it does NOT mean
  the secret is new."* Two Android keystore entries carry `no cadence (rotate on compromise)`.
  The check is deliberately non-strict for now; recording the first dates is owner **Action 1**.
- **Least-privilege notes found in source:** `daily_advisory_ingest.yml` sets
  `permissions: contents: write` (it commits); `secret-rotation-audit.yml` and
  `verify-secrets.yml` set `contents: read`. The Kaggle fetch step explicitly refuses to make a
  private secret mandatory for a public CSV.

### 4) Reliability and Failure Behavior

- **Retry / backoff:**

  | Where | Policy | Evidence |
  |---|---|---|
  | `packages/api` client (web + mobile) | `DEFAULT_RETRY_POLICY`: **maxRetries 5, base 1 000 ms, factor 2, full jitter, hard cap 1 h**; retryable statuses `{408, 409, 425, 429, 500, 502, 503, 504}` | `packages/api/src/retry.ts:25-33` |
  | Kaggle HTTP download | `attempts = 3`, `backoffMs = 20_000`; a 401/403 is **not** retried ("that means the key, not the network") | `scripts/fetch_kaggle_advisory.mjs:200,213-214` |
  | Kaggle fetch round | three methods in order: dataset over HTTP → dataset via CLI → kernel output via CLI; plus `--wait-minutes 12` polling so a tardy scheduled notebook is waited for, not failed | `scripts/fetch_kaggle_advisory.mjs:351-355`, `daily_advisory_ingest.yml` |
  | AI providers | per-provider timeout so "a hung upstream must not eat the whole cascade"; circuit breaker, `TRIP_COOLDOWN_MS = 45_000`; 429 trips and falls through; final deterministic heuristic | `backend/utils/ai_fallback_engine.js:25,39-109,466-512` |
  | Wind artifact | GFS first, ECMWF fallback | `scripts/fetch_live_wind.mjs`, `live-wind-update.yml` |
  | Analytics beacon | batching, queue cap, **one retry then drop**, `sendBeacon` on unload | `packages/analytics/src/streaming.ts` |
  | Playwright (E2E) | `retries: CI ? 2 : 0` — "retries absorb CI runner variance instead of masking real failures" | `playwright.config.ts` |

- **Timeout policy:**

  | Integration | Timeout | Where |
  |---|---|---|
  | Telegram | 8 000 ms default, `TELEGRAM_TIMEOUT_MS` | `backend/alerts/channels/telegram.js:27` |
  | SMS | 8 000 ms default, `SMS_TIMEOUT_MS`; plus `SMS_MAX_PER_RUN` = 25 and `SMS_DRY_RUN` | `backend/alerts/channels/sms.js:39-41` |
  | AI providers | per-provider timeout constant | `backend/utils/ai_fallback_engine.js:25` |
  | Express body parse | `express.json({ limit: '10mb' })` | `backend/server.js:104` |
  | CI jobs | `timeout-minutes: 25` (ingest), `15` (security-audit) | `.github/workflows/*` |
  | Playwright | `timeout: 60_000` per test | `playwright.config.ts` |
  | Kaggle freshness gate | `--max-age-hours 36` at fetch **and** at ingest (same gate, decided once, upstream) | `daily_advisory_ingest.yml` |

- **Circuit-breaker / fallback behaviour:**
  - AI: real circuit breakers with a 45 s half-open cooldown and a `getSystemStatus()` telemetry
    view of `{state, failures}` per provider.
  - Store: `firestoreAvailable` is a soft breaker — on failure it flips false, serves the
    committed snapshot, and re-probes on later calls (`backend/forecastStore.js:172-406`).
  - CORS: **fails closed** in production when `FRONTEND_ORIGIN` is unset.
  - API key: **fails closed** with 503 when `BACKEND_API_KEY` is unset.
  - Rate limiting: **per-instance only** on Vercel — `serverlessGuard.js` states the effective
    ceiling is `limit × instances`, and that a shared counter (Upstash/Redis) is owner Action 8.
    Buckets by cost, not by route, mirroring the Express limiters:
    `read 120/min`, `alerts 60/min`, `ai 20/min`, `pipeline 12/min` (**×10 = 120/min** when the
    request carries the pipeline key, so a chunked backfill cannot fail mid-run on a limit meant
    for anonymous probing), `metrics 60/min`.
  - The dependency-free design of `serverlessGuard.js` is deliberate: "a serverless cold start
    should not pay for a Redis client."

### 5) Observability for Integrations

- **Logging around external calls:** yes, consistently, with a bracketed scope tag —
  `[AI Fallback Engine]` names the provider and the reason it fell through; the Kaggle fetcher
  logs a *method-by-method diagnosis* and writes `fetch-report.json` (`age_hours`, `stale`) which
  the workflow then embeds in `$GITHUB_STEP_SUMMARY`; `utils/logger.js` provides
  `info/warn/error/debug` for the serverless handlers. Telegram explicitly
  **redacts its URL** (`redacted_url`) so the bot token cannot reach a log.
- **Metrics/tracing coverage:** `prom-client` gauges and counters in `backend/metrics.js`,
  exposed at `/metrics` (self-host) and `/api/metrics` (serverless, `read`-bucketed), including a
  forecast-age gauge refreshed by `refreshForecastAgeGauge()`. A request-id middleware
  (`backend/middleware/requestId.js`) correlates logs. **There is no distributed tracing** — no
  OpenTelemetry, no APM agent in any manifest.
- **Committed observability config:** `monitoring/prometheus.yml` (30 s scrape,
  `job_name: hazardnet-selfhost` → `localhost:3001`, with the Vercel job **commented out**),
  `monitoring/alerts.yml`, `monitoring/grafana-dashboard.json`,
  `docs/monitoring/grafana-dashboard.json`, `scripts/setup_monitoring.sh`,
  `MONITORING_SETUP_GUIDE.md` (396 lines).
- **Artifact-level observability (this repo's real strength):**
  - `frontend/public/data/freshness.json` — `schema: hazardnet-freshness/v1`, `built_at`,
    `generated_by`, a `what_this_is` paragraph that states its own limits (*"It is not a live
    probe and it does not measure the running services"*), and per-source
    `{id, label, artifact, state, reason, generated_at, prediction_date, age_hours}`.
    **Current state: `overall.state = "failing"`, counts `{fresh 1, stale 2, failing 1}`,
    `not_fresh: [forecast_ingest, forecast_snapshot, site_probe]`.**
  - `data/site-health/latest.json` — `schema: hazardnet-site-probe/v1`, seven checks
    (`homepage`, `deep_links`, `security_headers`, `sitemap`, `forecast_data`, `status_page`,
    `content_pages`). **Current state: `outcome: "fail"`, all seven `failure`, `detail: null`.**
  - `Models/VERSION.json` + `Models/REGISTRY.json` — a sha256/version **handshake** that CI
    verifies is committed and clean.
- **Missing visibility gaps:**
  1. **The site-health probe is blind, not the site down.** Measured 2026-10-09
     (`docs/audits/2026-10-09-cloudflare-403-origin-probe.md`, run 37870196679): every path —
     `/`, `www`, `/status`, `/sitemap.xml`, `/data/*`, `/api/*`, and a path that has never
     existed — returns `HTTP 403` with `server: cloudflare` and `cf-mitigated: challenge`,
     body `<title>Just a moment...</title>`. **No origin header ever appears** (no
     `x-fh-requested-host`, `x-served-by`, `x-vercel-id`, `cf-cache-status`, `age`), so no origin
     answers at all. A Chrome UA and a plain curl UA are challenged identically, which is why
     `PROBE_USER_AGENT` (PR #87) could never have helped. GitHub Actions egress is datacenter IP
     and cannot execute a JS challenge. The workflow side is **implemented** — a generated curl
     config sends `x-hazardnet-probe` from the `SITE_PROBE_TOKEN` secret, and `edge_challenged`
     is recorded in the artifact so a blocked probe is distinguishable from an outage. What
     remains is owner-side (Action 18): generate the token, add the Cloudflare WAF **Skip** rule
     above bot-management, store the secret.
  2. **The probe's failures have been committing artifacts for weeks** — 56 commits touched
     `data/site-health/latest.json` and 58 touched `frontend/public/data/freshness.json` in 90
     days, the two highest-churn paths in the repository, all machine-generated.
  3. **No metric or alert distinguishes "Kaggle did not publish" from "our pipeline broke."**
     The distinction exists only in the run summary and the Slack message.
  4. **Telemetry has no sink.** `POST /api/v1/telemetry` logs and acknowledges; nothing persists
     it (Action 12), so there is no product-side observability at all.
  5. **No APM/tracing** across the AI cascade, so per-provider latency and cost are only visible
     in log text and in the in-memory `getSystemStatus()` of one instance.
  6. **The Prometheus scrape target for the deployed surface is commented out**
     (`monitoring/prometheus.yml:30-34`), so only a locally-run self-host backend is scraped.

### The AI cascade, in order

`backend/utils/ai_fallback_engine.js:466-512` builds `cascadeProviders` and walks it:

```text
gemini_primary     Gemini            (GEMINI_API_KEY)
  -> gemini_secondary  Gemini backup (GEMINI_API_KEY_BACKUP)   [also used by liveVoice.js:130]
  -> openrouter        OpenRouter    (OPENROUTER_API_KEY)  several free slugs, cascading internally
  -> groq              Groq          (GROQ_API_KEY)
  -> huggingface       HuggingFace   (HUGGINGFACE_API_KEY)
  -> deterministic heuristic engine                            [no credential required]
```

The five keys above are the literal `cascadeProviders[].key` values from
`ai_fallback_engine.js:467-473`; they are also the circuit-breaker keys, so
`isProviderHealthy(key)` and `getSystemStatus()` report per-tier state under exactly these names.
A **10-minute** advisory cache sits in front of the whole cascade
(`CACHE_TTL_MS = 10 * 60 * 1000` at `ai_fallback_engine.js:23`; the lookup and
`engineStats.cacheHits` increment are at `:458-464`, keyed on
`district:hazard:round(severity*10):promptHash`), so a repeated advisory need not spend a
provider at all.

Each tier is skipped when its key is absent (`throw new Error('<KEY> not configured')` inside the
tier, caught by the loop) or when its breaker is tripped. `backend/server.js:44` downgrades a
missing `GEMINI_API_KEY` to a **warning**, not a problem, precisely because the heuristic tier
exists. Grounding (search / Maps) is a separate path — `backend/utils/gemini_grounding.js` with
`detectGroundingIntent`, `executeSearchGrounding`, `executeMapsGrounding`.

### Region / failover topology notes

There is no multi-region topology in the repository. The failover that exists is
**provider-level and store-level**, not regional: Kaggle HTTP → Kaggle CLI → Kaggle kernel;
GFS → ECMWF; Firestore → committed snapshot → (tests only) memory; five LLM providers →
heuristic. The one genuinely unresolved topology question is which platform serves the apex
domain — Vercel and Firebase Hosting are both configured, and measurement on 2026-10-04 said
Firebase while the code declares Vercel and a `www` canonical that does not resolve
(Actions 16 and 17; the owner decided on 2026-10-04 that `www` stays canonical and deploys stay
with Vercel, owner-run).
