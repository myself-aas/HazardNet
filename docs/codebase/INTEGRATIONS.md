### 3) Secrets and Credentials Handling

- **Credential sources**:
  - Local: `.env` (git-ignored — `.gitignore` lists `.env`, `.env.*`, `!.env.example`), loaded by `dotenv.config()` in `backend/server.js` and `backend/db.js`.
  - `FORECAST_STORE` is the Firestore selector and `scripts/validate_env.mjs` accepts only `['firestore','local','memory','json']`; `.env.example` now ships the valid `FORECAST_STORE=firestore`, so the CI `check:env` gate passes on the documented value. See CONCERNS §1.
  - Fixture: `firebase-applet-config.json` is **tracked** and supplies the server's Firebase project id, api key and `firestoreDatabaseId`.
  - Deployed: Vercel project environment variables (documented in `VERCEL_ENV_TEMPLATE.md`); GitHub Actions secrets for the pipelines; `.env.example` is the single tracked template (88 lines) and labels values as `REPLACE_WITH_…` placeholders.
  - Browser-exposed values are explicitly grouped and marked "public by design" — `VITE_FIREBASE_*`, `VITE_VAPID_PUBLIC_KEY`, `VITE_ADSENSE_*`, `VITE_VERCEL_ANALYTICS`.
- **Hardcoding checks**:
  - `firebase-applet-config.json` and `frontend/src/lib/config.ts` both contain the live Firebase web config literals (api key `AIzaSy…`, app id, project id, measurement id). This is documented as intentional ("Firebase web configs are public-by-design") in `frontend/src/lib/config.ts`, and the same literals appear in `.env.example`.
  - `.env.example` records that real provider keys previously accumulated there and were replaced with placeholders; the file states the originals "exist in git history" and **must be rotated** (cross-reference: `docs/audits/2026-09-18-secret-scan-false-negative.md`).
  - An automated gate exists: `bash scripts/check-secrets.sh` runs in the CI `security-audit` job and scans the working tree for `ghp_`/`sk-`/`AIza`/`xox`/`AKIA`/private keys/password-bearing connection strings. It is explicitly **working-tree only** — history is out of scope by design.
- **Rotation / lifecycle**: no rotation automation found. `docs/audits/2026-09-18-secret-scan-false-negative.md` is cited as the tracking document for the historical exposure; `.github/workflows/verify-secrets.yml` and `scripts/verify-actions-secrets.sh` exist to validate that required Action secrets are present. `[TODO]` — no evidence of a scheduled rotation policy.

### 4) Reliability and Failure Behavior

- **Retry/backoff**: no generic HTTP retry wrapper. Resilience is concentrated in the AI layer — provider circuit breakers trip on 429/quota for 45 s (`backend/utils/ai_fallback_engine.js`), and the cascade advances to the next tier. `backend/utils/openMeteo.js` instead relies on a TTL cache plus a batch endpoint that collapses 64 district requests into one upstream call.
- **Timeout policy**: the most explicit budget is the AI layer — `PROVIDER_TIMEOUT_MS = 12_000` per provider in `backend/utils/ai_fallback_engine.js`, chosen because "a hung upstream must not eat the whole cascade (the chat serverless function has a hard wall-clock budget on Vercel)". `ALERT_NOTIFY_TIMEOUT_MS` is configurable for alert delivery (`.env.example`). `[TODO]` — no documented global HTTP timeout for the Open-Meteo or Firestore clients.
- **Circuit-breaker / fallback behavior**: four independent degradation ladders are implemented:
  1. AI: Gemini primary → Gemini backup/key rotation → OpenRouter → Groq → HuggingFace → deterministic heuristic engine (every response stamped with `provider_source`).
  2. Forecast data: API → committed `forecasts-latest.json` snapshot → static `ALL_64_DISTRICTS` baseline (`frontend/src/hooks/useForecasts.ts`).
  3. Model runtime: `@tensorflow/tfjs-node` native → `@tensorflow/tfjs` CPU fallback (`backend/tfjs.js`).
  4. `hazard_type` labels: `Models/labels.json` → built-in 8-class literals (`backend/inference.js`).
- **Fail-closed defaults** (misconfiguration denies rather than allows): `verifyApiKey` → 503 when `BACKEND_API_KEY` is unset; CORS refuses cross-origin in production when `FRONTEND_ORIGIN` is unset; CSP enforces in production by default (`backend/server.js`).

### 5) Observability for Integrations

- **Logging around external calls**: yes, partially. Every AI provider response is tagged with `provider_source` and surfaced to the user, so the answering engine is visible in-product (`backend/utils/ai_fallback_engine.js`). Errors funnel through `clientError`/`logServerError`, which log a `[scope]`-tagged stack server-side while returning a generic message to the caller (`backend/utils/clientError.js`). Requests carry a correlation id via `X-Request-Id` (`backend/middleware/requestId.js`).
- **Metrics/tracing coverage**: Prometheus metrics via `prom-client` in `backend/metrics.js` — `inference_latency_ms` (histogram, 7 buckets), `prediction_accuracy_per_class`, `severity_mae`, `model_load_time_ms`, `api_requests_total`, `cache_hit_rate`, and `hazardnet_forecast_age_hours` (the freshness SLO gauge). Exposed at `GET /metrics` on the Express server (`backend/server.js`) and at `/api/metrics` on Vercel (`api/metrics.js`). Scrape config, alert rules and a Grafana dashboard are committed: `monitoring/prometheus.yml`, `monitoring/alerts.yml`, `monitoring/grafana-dashboard.json`. The SLO is defined numerically: 2–170 h healthy weekly cadence, `>192 h` → `HazardNetForecastStale`, absent series → `HazardNetForecastDataMissing` (`monitoring/README.md`).
- **Missing visibility gaps**:
  - No tracing/APM (no OpenTelemetry, Datadog or Sentry dependency in either manifest) — a failed request is visible only through its log line and `X-Request-Id`.
  - Per-provider AI failure/fallback counts are not exported as metrics; the circuit-breaker state is in-process only and resets on every cold start.
  - The Open-Meteo proxy and Firestore reads export no dedicated latency/error metric, so upstream degradation is not directly graphable.
  - The `monitoring/` stack is committed but has no deployment evidence in-repo (no compose/k8s manifest — the scan reports "No containerization configs detected").
