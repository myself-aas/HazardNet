## Core Sections (Required)

### 1) Architectural Style

- **Primary style: layered, with a deliberate dual-transport split.** The repository ships *two* HTTP surfaces over one shared core:
  1. a self-hosted **Express** server (`backend/server.js`), and
  2. **Vercel serverless** handlers (`api/**/*.js`) that `import` the same `backend/` modules.

  The duplication is explicit and managed: `backend/utils/forecastServe.js` and `backend/utils/chatService.js` each document that they exist so "the Express route and the Vercel serverless functions behave identically **by construction**".
- **Why this classification**: `backend/` is organised strictly by layer (`routes` → `utils`/`services` → `forecastStore` → `db`), not by feature. A datastore adapter (`forecastStore.js`) is the only module that touches Firestore for forecasts, and routes are thin (e.g. `api/v1/forecasts/bulk.js` is ~874 LOC across the whole `api/` tree for 15 handlers).
- **Primary constraints that shape the design**:
  1. **Serverless execution** — no long-lived in-process state may be assumed; the chat function ships the RAG corpus via `includeFiles: ../rag_pipeline/**` (`vercel.json`) instead of reading a volume.
  2. **Runs on free tiers** — the AI layer is a six-tier fallback cascade with circuit breakers (`backend/utils/ai_fallback_engine.js`) rather than a single paid provider.
  3. **Safety-critical output** — the alert engine forbids auto-publication above `WATCH` and refuses `WARNING` without calibrated probability, enforced in the store and policy objects rather than by convention (`backend/alerts/policy.js`, `backend/alerts/store.js`).

### 2) System Flow

```text
[1] GitHub Actions (daily_forecast.yml, cron 0 0 * * *)
        └─ scripts/auto_forecast.py : GEE imagery + Open-Meteo → TFLite inference
[2] scripts/publish_forecast_csv.py  → backend/data/forecasts/hazardnet_forecasts_latest.csv
        └─ scripts/build_forecast_snapshot.mjs → frontend/public/data/forecasts-latest.json (committed)
        └─ optional: POST /api/ingest with Bearer BACKEND_API_KEY
[3] api/ingest.js → verifyApiKey (timing-safe, fail-closed 503) → csvIngestion → forecastStore.appendForecasts
        └─ backend/forecastStore.js → backend/db.js → Firestore collection `forecasts`
[4] api/v1/forecasts/bulk.js  (or backend/routes/forecasts.js on Express)
        └─ backend/utils/forecastServe.js → forecastStore → Firestore
[5] React SPA: frontend/src/hooks/useForecasts.ts → TanStack Query
        └─ falls back to the committed /data/forecasts-latest.json, then to the static ALL_64_DISTRICTS baseline
[6] Alert path: backend/alerts/service.js → assessBatch → DRAFT → auto-publish (≤ WATCH) | PENDING_REVIEW (> WATCH)
        └─ backend/alerts/notify.js → channels/sms.js, channels/telegram.js
```

Steps 1–6 are each backed by the cited file. Note the **two independent delivery channels** in steps 2–3: the website is served the *committed snapshot* by default, while the API/store path is opt-in (`PUSH_TO_API` repository variable, per the `daily_forecast.yml` header comment).

### 4) Reused Patterns

| Pattern | Where found | Why it exists |
|---------|-------------|---------------|
| **Singleton (lazy, resettable)** | `getForecastStore()` / `resetForecastStore()` in `backend/forecastStore.js`; `getTf()` cached module in `backend/tfjs.js`; prediction cache in `backend/utils/predictionCache.js` | One model instance / one store instance per process; the reset hooks exist for tests |
| **Adapter / repository** | `backend/forecastStore.js` exposes `getForecastStore().mode` and a fixed method set over Firestore | Historically decoupled Firestore ↔ Supabase (ADR 0002 cutover); callers are store-agnostic |
| **Shared-implementation-for-two-transports** | `backend/utils/forecastServe.js`, `backend/utils/chatService.js` | Closes the Express/Vercel API-parity gap "by construction" rather than by review |
| **Circuit breaker** | `circuitBreakers` map in `backend/utils/ai_fallback_engine.js` (trips on 429/quota for 45 s) | Free-tier providers rate-limit; a tripped provider must not eat the request budget |
| **Cascade / chain of responsibility** | Six-tier provider cascade in `ai_fallback_engine.js` ending in a deterministic heuristic engine; every response stamped with `provider_source` | Guarantees an answer even when all LLM providers fail, and makes provenance visible to the user |
| **State machine with an explicit policy object** | `ALERT_LEVELS` + `applyTransition`/`evaluateTransition` (`backend/alerts/lifecycle.js`), policy-as-data (`backend/alerts/policy.js`) | A threshold change is a reviewable config change; each alert records the `policy_version` that produced it |
| **Build-time artifact projection with `--check`** | `build_content_engine.mjs --check`, `build_freshness_artifact.mjs --check`, `build_model_performance.mjs --check` | CI asserts the committed artifact still describes the committed inputs (clock-blind, so it cannot rot) |
| **Fail-closed security defaults** | `verifyApiKey` returns 503 when `BACKEND_API_KEY` is unset; CORS rejects cross-origin in production when `FRONTEND_ORIGIN` is unset | A misconfigured deploy should deny rather than silently allow |
| **Lazy route-level code splitting** | `React.lazy` + `<Suspense>` in `frontend/src/App.tsx` | Keeps the initial bundle inside the `check:bundle` budget |

### 5) Known Architectural Risks

- **Two HTTP surfaces must stay in parity.** Express routes and Vercel handlers are separate files; parity holds only where a shared module was extracted. Where it was not (`backend/routes/predict.js`, `push.js`, `conversions.js`, `weather.js` have no `api/v1` twin except `weather`), behaviour can diverge by transport. Impact: a bug fixed on one surface stays live on the other.
- **Client-side fallback can silently serve stale data.** `useForecasts.ts` degrades API → committed snapshot → static baseline without surfacing which source answered at the *hook* level (the alert surface does label its source). Impact: a dead pipeline can look like a working one.
- **The forecast store is reached with the *client* Firebase SDK server-side** (`backend/db.js` imports from `firebase/firestore`; `firebase-admin` exists but is used only by `backend/middleware/firebaseAuth.js` to verify ID tokens, and no auth context or Admin credential is attached to the store client). Access control therefore rests entirely on `firestore.rules`, which grants `allow get, list: if true` but `allow create, update, delete: if false` on `/forecasts` — so the read path works and the *write* path is denied by rule. The rules' own comment assumes the exemption that only the Admin SDK would provide. Impact and the surrounding `FORECAST_STORE` gap are written up in CONCERNS §1.
- **Committed-snapshot delivery means a stale commit is a stale product.** The website's default data path is `frontend/public/data/forecasts-latest.json`; if the daily workflow fails to commit, no runtime error occurs — the site simply serves older data. The `hazardnet_forecast_age_hours` gauge exists to detect this, but it is not a deploy-blocking gate.
- **Architectural intent is ahead of implementation, and the gap is documented in more than one place.** ADR 0005 accepts ADM3/507-unit expansion and 10/20/30-day horizons, but `README.md` states the implementation still runs 64 districts and 7/15 days only, guarded by `scripts/tests/test_model_claims.py`. Separately, ADR 0002 documents a merged `FORECAST_STORE=firestore|supabase` selector with a Supabase store implementation, a migration script, a `002_forecasts_supabase.sql` schema and a 16-test suite — none of which exist in the tree; `getForecastStoreMode()` returns a literal `'firestore'` and `process.env.FORECAST_STORE` is read nowhere in `backend/` or `api/`. Impact: readers of the ADRs can overstate the shipped product, and operators following `api/v1/forecasts/bulk.js` will set an env var that does nothing.
